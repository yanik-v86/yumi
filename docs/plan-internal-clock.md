## 0. Что и зачем

Юми нужен **один внутренний механизм времени**, который умеет:

- хранить текущее время и тикать в уже существующем кадре приложения;
- планировать отложенные и повторяющиеся задачи;
- откладывать (`defer`) и пропускать (`skip`) задачи;
- давать другим подсистемам Юми точки входа (`register`/`schedule`) для своих
  задач — пользовательским интентом, напоминаниям, перерывам, hourly chimes,
  встроенному таймеру и будущим фичам.

**Важно:** часы сами по себе ничего не знают об интентах, фразах, напоминаниях
или web-панели. Это инфраструктура времени. Бизнес-логику подключают
потребители через хендлеры.

### Не цели этого этапа

- Не логировать действия интентов — это отдельная задача
  `plan-intents-action-log.md`.
- Не делать редактор напоминаний/задач в web-панели и GTK. Панель получает
  только read-only статус часов.
- Не добавлять второй `GLib.timeout_add`: источник тика один — `App.frame()`
  → `Brain.update()`.
- Не переписывать существующий `Brain.timer` за один шаг: сначала часы
  сосуществуют с ним, перенос потребителей идёт по одному.

## 1. Состояние до старта

- `App.frame()` вызывает `Brain.update(time.monotonic())`; внутри — `timer_update()`
  и `extras_update()`. Отдельные `GLib.timeout_add_seconds(3600)` / `(4)` живут
  вне этого цикла и не должны множиться.
- `Brain.timer` — Scroll-таймер, со своим состоянием и звуком. `yumi/extras.py`
  содержит `breaks` и hourly chimes — примеры «почти напоминаний».
- Единого сервиса времени, таблицы задач и General-хуков нет.
- В `DEFAULT_SETTINGS` нет ключей часов; в `/api/status` нет статуса времени.
- В рабочем дереве есть незакоммиченные правки `yumi/brain.py` и `yumi/ui/app.py`
  с `extra_env={'YUMI_INTENT_TEXT': heard}` — к часам отношения не имеют,
  сохраняем как есть.

## 2. Архитектура одним взглядом

```
App.frame()
  │  Brain.update(now_monotonic)
  ▼
brain.py ──▶ Clock.tick(now_wall, now_monotonic) ──▶ fired events
                 │                                      │
                 ├─ Clock.register(kind, handler) ───────┤
                 ├─ Clock.schedule(kind, ...)            │
                 └─ ClockStore (только persist=True)     │
                                                        ▼
                      consumer'ы: timer / breaks / chimes / intents / future
```

`yumi/clock.py` и `yumi/clock_store.py` — чистые модули: без GTK, без HTTP,
без импорта `Brain` и без бизнес-правил потребителей.

### C-01. Ядро часов (P0) — TODO

**Файлы:** `yumi/clock.py` (новый), `tests/test_clock.py` (новый).

**Что сделать:**

### C-02. Тик и время (P0) — TODO

**Файлы:** `yumi/clock.py`, `tests/test_clock.py`.

**Что сделать:**

- `tick(now_wall, now_monotonic)` возвращает список fired-событий и сам вызывает
  зарегистрированные хендлеры. Порядок: взять due → пометить `fired` → сдвинуть
  `due_at` → вызвать handler.
- Идемпотентность: два тика с одним и тем же `now_wall` не дают двойного вызова.
- `every_s=0` — одноразовая задача; после срабатыванияjob удаляется из активных
  (или помечается `done` — выбрать и зафиксировать тестом).
- `defer_until` имеет приоритет над `due_at`; `skip()` сдвигает ближайшее
  срабатывание, не удаляя повтор.
- Окно просрочки `MISSED_WINDOW_S = 900`: если job просрочена больше чем на
  15 минут, она не выполняется, а отдаётся как `missed`.
- `now_wall` (epoch) используется для `due_at`; `now_monotonic` — только для
  длительностей и диагностики. Не смешивать.

**Критерии приёмки:** задача сработала ровно один раз; `cancel()` предотвращает
повтор; повтор с `every_s` не дублируется; просрочка >15 мин не выстреливает
в прошлое.

### C-05. Хуки и адаптеры (P0) — TODO

**Файлы:** `yumi/clock.py`, `yumi/brain.py`, `tests/test_clock.py`.

**Что сделать:**

- `register(kind, handler)` — один handler на `kind`, повторная регистрация
  заменяет его. `on_error` — callback для диагностики.
- `schedule(kind, *, in_s=None, due_at=None, every_s=0, owner='', payload=None,
  persist=False, id=None)` — единая точка планирования. `in_s`
  нормализуется в абсолютный `due_at` в момент вызова.
- Адаптеры существующих потребителей регистрируются в `Brain`: `timer`,
  `breaks`, `hourly_chimes`. На первом шаге можно оставить их старую логику
  и просто вызвать её из хендлера, не переписывая.
- `defer(job_id, delay_s)`, `skip(job_id)`, `cancel(job_id)` доступны всем
  consumer'ам.

**Критерии приёмки:** handler можно заменить через `register()`; исключение
в одном handler'е не останавливает остальные и уходит в `on_error`; адаптер
таймера вызывает ту же логику, что и раньше.

## 6. Definition of Done

- [ ] Тик один: `App.frame()` → `Brain.update()` → `Clock.tick()`; новых

      сдвигаются; просрочка >15 мин не выполняется.

## 7. Открытые вопросы (решить до C-05)

1. **Одноразовая задача после срабатывания:** удалить из active или оставить
   с `status=done` для истории? Рекомендуется удалять, историю не хранить.
2. **Кто владеет `now_wall`:** часы сами вызывают `time.time()` или получают
   его от `Brain`? Рекомендуется передавать оба времени в `tick()` — проще
   тестировать.
3. **Файл персистентности:** `STATE_DIR/clock-jobs.json` или всё же в
   `CONFIG_DIR`? Рекомендуется `STATE_DIR`, потому что это состояние, а не
   пользовательский конфиг.
4. **Приоритет defer/skip:** рекомендуется `defer_until` важнее `due_at`;
   `skip` двигает только ближайшее срабатывание.
5. **Имя класса:** `Clock` vs `TimerService`. Рекомендуется `Clock`, чтобы не
   путать с `Brain.timer`.
